# 데이터 수집기 인계

## 실행과 담당 경계

기존 진입점 `update_daily_candles() -> None`, `collect_news() -> None`을 유지한다.
스케줄러는 기존 방식으로 이 함수를 부른다. 수집기만 실행할 때는 저장소 루트에서:

```powershell
python -c "from data_collector.collector import update_daily_candles; update_daily_candles()"
python -c "from data_collector.collector import collect_news; collect_news()"
python -m pytest -q
```

첫 명령은 전체 종목을 수집하므로 수십 분 걸릴 수 있다. 실제 주문은 호출하지 않는다.
뉴스 자동 수집은 오늘 후보와 수량이 양수인 보유 종목만 대상으로 한다.
후보 선정·LLM 판단·주문·청산 모듈은 다른 담당자의 구현을 사용한다.

## 일봉

- AQuA 전체 종목 목록을 대상으로 한다. 유동성 상위 300개 선정은 전략 담당이다.
- 최초에는 KST 오늘을 제외한 최근 달력 1년을 적재한다. 전략 설정상 필요한 봉수가
  부족하면 그보다 과거를 더 받아 현재 최소 250봉을 확보한다. API 커서로 이어받는다.
- 이후에는 마지막 저장일보다 새로운 일봉만 추가한다. 같은 날 재실행해도 기존 행을
  덮어쓰지 않는다. 오래 쉬었다면 마지막 저장일까지 이어받는다.
- 기존 데이터의 가격 정정이나 중간 누락 복구는 증분 갱신의 범위가 아니다.
- 종목 단위로 검증 후 저장한다. 실패한 종목은 이번 데이터를 저장하지 않고 나머지를
  수집한 뒤 오류를 발생시켜 불완전한 입력으로 후보 선정이 진행되지 않게 한다.
- 최신 페이지가 비어 있으면 기존 DB가 있어도 갱신 성공으로 처리하지 않는다.
- 날짜는 `YYYY-MM-DD`, OHLCV는 정수다. 시간대 없는 원본 시각은 거부한다.
- 최근 달력 1년과 전략 설정의 250봉은 다르다. 실제 2026-10-23 조회에서는 일반 종목도
  244봉이었다. 사용자 요청에 따라 최소 250봉까지 과거 구간을 확장했다. 저장된 이력이
  최소 봉수보다 짧으면 다음 수집에서도 보충을 시도한다. 신규 상장 등으로 공급자가
  제공하는 이력이 부족하면 경고를 남긴다. 전략 담당은 부족한 종목을 제외·보류해야 한다.
- 새벽 실조회 성공으로 장 전 수집이 가능함을 확인했으며 기존 08:00 설정을 유지한다.
  학교 서버에서 해당 시각에 예약 작업이 실행되는지는 후속 운영 검증 대상이다.

## 기존 스케줄러와 운영 기간

- 스케줄러는 팀장 소유의 기존 `main.py`를 사용하며 이번 변경에 포함하지 않는다.
- 평일 08:00 장 전 작업, 09:30·11:00·13:00 재평가를 실행한다.
- 청산 감시는 안내 PDF 5쪽에 명시된 09:00~14:45, 15분 간격이다. 15:00 정각은 제외한다.
- 주말과 `schedule.holidays`에 등록된 날짜를 건너뛴다. 현재부터 2026년 11월 말까지
  예정된 평일 휴장일이 없어 `holidays: []`를 유지한다.
- 서버 통합 시 서버 시간대가 KST인지 확인한다. 기존 휴장일 판단은 서버의 로컬 날짜를 쓴다.

## 뉴스

- Google News RSS 검색을 사용하며 별도 뉴스 API 키를 전송하지 않는다.
- `config.yaml`의 `news`에서 조회 기간·요청 시간·별칭·제외어를 관리한다.
- `published_at`, `collected_at`은 초 단위 ISO 8601 KST 문자열이다.
  예: `2026-10-23T09:30:00+09:00`. 발행 시각이 수집 시작 이후인 기사는 제외한다.
- `news_id`는 SHA-256(`symbol + '\n' + RSS URL`)이다. 동일 종목·URL은 중복 저장하지
  않고 최초 수집 시각을 유지한다. 다른 종목에도 관련된 기사는 종목별로 저장한다.
- RSS 조회 실패는 빈 뉴스 목록으로 취급하지 않고 오류를 발생시킨다.
- 제목 매칭은 의미 분석이 아니다. 계열사·동명이인 오탐은 샘플을 점검하고
  별칭·제외어로 조정한다. URL이 다른 동일 기사까지 합치지는 않는다.
- NLP 담당은 판단 시 `published_at <= run_at`을 적용하고 기사 중요도를 판단한다.

## 공통 API와 DB

- AQuA 인증·조회·재시도는 `common.aqua_client`의 공통 요청 함수를 통과한다.
- 토큰 만료 1시간 전 또는 조회의 401 응답에서 재로그인한다.
- 호출 제한은 프로세스 내 이동 60초 기준이며 설정값은 80회다. 여러 프로세스나
  팀원의 PC에서 같은 계정으로 동시에 대량 조회하면 합산 제한은 보장하지 못한다.
- 호출 제한 429는 Retry-After 후 1회, 시세 장애 502는 잠시 대기 후 1회 재시도한다.
  지속되는 실패는 `AquaError`로 전달한다. 주문은 자동 재전송하지 않는다.
- 주문·취소 함수, 스케줄러, DB 스키마는 이번 구현에서 변경하지 않았다.
- 다른 담당자는 기존 `init_db()`와 `with connect() as conn:`을 사용한다.
  SQL 값은 파라미터로 전달한다. 정상 종료 시 커밋, 예외 시 롤백된다.

## 검증 범위

자동 테스트는 가짜 HTTP 응답과 임시 DB를 사용한다. 실제 클라이언트·수집기 연결,
토큰 갱신, 호출 제한, 오류 전파, 일봉 이어받기, 뉴스 중복 제거를 검증한다.
`main.py --once all` 경로의 순서 검증에는 타 담당 함수 대신 fixture를 사용한다.
이는 타 담당자의 실제 구현을 합친 학교 서버 통합 완료를 의미하지 않는다.

운영 DB·.env·로컬 검증 보고서는 커밋하지 않는다. WAL/SHM 부속 파일도 포함하지 않는다.

## 2026-10-23 실제 검증 결과

- 인증·조회 API 및 캔들 200개씩 이어받기 성공. 실조회는 02시대에 수행했으며
  08시 스케줄 실행을 확인한 것은 아니다.
- 전체 801종목, 199,846행 적재. 최소 250봉 기준으로 보충한 전체 수집은
  02:19:56~02:45:08 KST, 약 25분 12초였다. 시작 시 200종목 48,800행이 이미 있었다.
- 최종 검증에서 누락 종목·OHLCV 범위 및 날짜 검사 오류는 0건, SQLite integrity_check는 ok.
  모든 종목의 마지막 일봉은 2026-10-22이다.
- 14시대에 대표 4종목을 재실행한 결과 전체 일봉 DB 내용이 동일했다(약 4.41초).
  전체 종목의 일일 증분 실행 시간을 측정한 결과는 아니다.
- 796종목이 250봉 이상이다. 공급 이력이 짧은 5종목은 아래와 같다.

| 종목 코드 | 확보 봉수 |
| --- | ---: |
| 0120G0 | 222 |
| 0126Z0 | 222 |
| 0220W0 | 39 |
| 217590 | 207 |

- 대표 4종목 RSS 뉴스 363건 저장. 검사한 시각 오류 0건, 같은 행 재저장 시 신규 0건,
  기존 내용 동일. 종목명은 앞서 실조회한 목록을 재사용해 일봉 수집과 AQuA 호출이 겹치지 않게 했다.
- 실제 자동 뉴스 대상은 후보·보유 종목이 없어 0개였다. 대상이 있는 합집합 처리는
  모의 테스트로 검증했으며, 후보가 생성된 뒤 실제 자동 수집을 다시 확인해야 한다.
- 코드 재검토 후 자동 테스트 82개 통과. 빈 최신 캔들 응답, 잘못된 시각의 종목별 오류 처리,
  호출 제한 설정 검증을 보강하고 증분 테스트가 실제 증분 경로를 거치도록 수정했다.
  이는 원천 거래소 가격과의 전수 대조나 학교 서버 통합 완료를 뜻하지 않는다.
- 원격 최신 main 확인은 이번 세션에서 조회 승인이 거절되어 수행하지 못했다.
  커밋·푸시·PR 게시 전 별도 확인이 필요하다.
